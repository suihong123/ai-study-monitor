# 项目迭代与优化前复盘机制

## 1. 目的

每次优化先恢复共同上下文，再讨论方案。这样可以避免：

- 只看局部页面，破坏访问码、会话、额度、成本或报告闭环；
- 把规划、Mock 或历史文案当作当前事实；
- 没有业务目标就直接堆功能；
- 改完代码却没有更新产品和数据口径；
- 多轮沟通反复解释同一套项目背景。

## 2. 哪些工作必须复盘

以下工作开始前必须建立一份复盘记录：

- 新功能、产品流程、交互或文案策略变化；
- 套餐、额度、有效期、访问码和运营规则变化；
- 识别模型、提示词、调频、提醒或报告变化；
- 指标、数据表、迁移、日志和后台变化；
- 鉴权、隐私、风控、部署、性能或架构变化；
- 修复会影响业务结果或数据口径的缺陷。

纯解释、只读排查和不会改变行为的极小修正可不创建文件，但仍需核对基线。紧急线上故障允许先止损，同一轮补齐复盘。

## 3. 固定流程

### 阶段 A：恢复基线

1. 阅读：
   - `docs/PROJECT_BASELINE.md`
   - `docs/BUSINESS_STATUS.md`
   - 最近 1–3 份 `docs/reviews/` 记录
2. 检查当前分支、未提交变化和最近提交。
3. 阅读本次相关代码、数据库和已有文档。
4. 将信息分为：
   - 已确认事实；
   - 需要验证的判断；
   - 当前未知或阻塞项。

### 阶段 B：优化前复盘

复制 `docs/reviews/TEMPLATE.md`，创建：

`docs/reviews/YYYY-MM-DD-简短主题.md`

至少回答：

- 当前阶段和这次触发问题是什么？
- 影响哪个角色、哪段核心闭环和哪个指标？
- 证据是什么？没有证据的部分是什么假设？
- 本次目标、范围和不做事项是什么？
- 业务规则和数据口径是否会变化？
- 如何验收？如何观察是否真的变好？
- 有哪些风险、回滚方式和待确认项？

### 阶段 C：先沟通，再实施

向项目负责人先给出一份简洁开场：

1. 当前基线；
2. 发现的问题与证据；
3. 业务影响；
4. 建议目标、范围和不做事项；
5. 验收标准；
6. 需要确认的关键决策。

如果没有会显著改变方向的待确认项，可以说明采用的合理假设并直接继续；如果套餐、收费、隐私、数据删除或核心业务规则不明确，不应擅自决定。

### 阶段 D：实施与验证

按风险选择验证强度：

- 业务规则：单元/集成测试 + 数据迁移验证 + 边界用例。
- 监督主链路：真实手机浏览器 + 摄像头 + 声音 + 异常退出。
- 报告指标：固定样本输入 + 预期口径对照。
- 后台操作：权限、操作前后数据、审计日志和失败路径。
- 文档/文案：链接、口径和页面实际展示核对。

任何数据库变化都要同时考虑：

- 新环境完整 schema；
- 已有环境增量 migration；
- 旧数据兼容；
- 幂等与回滚；
- 后台和报告口径。

### 阶段 E：回写基线

完成后：

1. 在复盘文件填写实际改动、验证结果、遗留问题和观察窗口。
2. 更新 `docs/reviews/README.md`。
3. 如果功能、规则、指标或风险状态改变，同步更新项目/业务基线。
4. 记录新的决策和被否决方案，避免未来重复讨论。

## 4. 优先级判断

建议按以下顺序判断工作是否值得做：

1. 是否影响儿童安全、隐私、权益或数据正确性？
2. 是否影响完整监督闭环能否成功？
3. 是否影响识别与报告是否可信？
4. 是否能减少家庭使用摩擦或运营人工成本？
5. 是否能提高可信监督的复用和付费？
6. 是否只是视觉偏好或局部技术洁癖？

优先处理更接近前四项的工作。

## 5. 完成定义

一项优化只有同时满足以下条件才算完成：

- 目标行为已经实现，异常路径没有明显退化；
- 有与风险相称的验证证据；
- 业务规则和指标口径没有模糊冲突；
- 相关基线和复盘记录已更新；
- 已说明未解决问题、上线条件和观察指标；
- 若影响线上数据，已有迁移、兼容和回滚考虑。

## 6. 当前迭代状态与下一步

第一轮“统一套餐权益与会话结算”已在 v0.7 生产环境完成：

- 所有套餐永久有效，仅按总时长控制；
- 会话由服务端计时，结算原子、幂等；
- 核心调用会检查本次未结算时长；
- 套餐统一真实基础报告；
- 增加隐私确认、锁文件、测试和 CI。

生产迁移、GitHub 自动检查、Vercel 部署和页面烟雾验收均已通过，当前状态为真实使用观察。下一步先用专用测试访问码覆盖手机摄像头、Qwen、额度耗尽和异常退出，再建立真实使用与质量基线；不应在没有数据前直接扩展高级报告。

第二轮“监督与报告信息层级”已在 v0.8 生产环境完成：

- 监督详情默认折叠并改用家长可理解的表达；
- 结束页只展示本次监督小结；
- 完整报告优先展示最近最多 7 次可信监督趋势并支持打印；
- 短时、低覆盖或 Mock 监督不进入近期趋势。

GitHub 自动检查、Vercel 正式部署、首页版本和真实历史趋势报告均已验收。下一步通过 3～5 次真实家庭监督观察页面理解度、报告复用和打印效果。

第三轮“使用环境重新绑定”已完成 v0.9 功能、自动测试、隔离/托管 PostgreSQL、Preview、生产迁移、真实 Qwen 和最终真机烟雾验收，已在生产发布：

- 浏览器 `localStorage` UUID 只代表使用环境，不宣称识别物理设备；
- 首次激活和同环境进入不计次数；
- 默认任意连续 15 天最多成功重新激活 10 次，两次成功至少间隔 60 秒；
- 所有重新激活免费，不扣访问码或会话监督时长；
- 数据库事务负责服务端时间、并发、幂等、滚动计数、环境更新、旧令牌失效和日志；
- 后台可配置窗口/上限/间隔，查看环境详情、历史与异常标记，并可填写原因后人工重置。
- 监督页已增加分析、心跳、校准纠错和报告请求取消；旧响应同时受客户端会话版本和数据库令牌事务门禁保护，不得写识别记录或 AI 日志。
- 已接受 Known Limitation：真实 Qwen 上游已开始处理后发生 Abort 时，无法实机证明连接立即终止；业务数据零影响，极端情况下可能多一次模型调用费用，不作为 v0.9 发布阻断项。

隔离数据库证据和真机执行表位于 `docs/acceptance/`。生产已按只读快照 → 显式事务 migration 18 → verify 18 → migration 19 → verify 19 → 最终一致性检查 → 应用部署 → 多浏览器/双设备验收完成。

第四轮小版本“Supabase Free Plan 每日只读保活”已通过 v0.9.1 Preview 验证：

- 新增 `CRON_SECRET` 保护的 `/api/cron/keep-alive`；
- 每天只读取一次 `access_codes.id limit 1`，不写业务数据；
- 不改变监督、重新绑定、计时、Qwen、报告或数据库结构；
- Preview 已确认未授权 401、授权 200、真实只读查询和零业务写入；Production 发布已获负责人确认。
