# 优化前复盘：项目优化路线选择

> 日期：2026-07-27
> 状态：已选择
> 负责人：项目负责人
> 关联范围：套餐权益、会话结算、报告、隐私、指标、工程质量、商业化

## 1. 当前基线

- 当前阶段：产品闭环较完整的 MVP，商业系统和真实业务数据基线尚未建立。
- 当前代码：`07f7d42`，工作区另有本轮项目基线和文档整理变更，尚未修改运行时业务代码。
- 核心闭环：运营创建访问码 → 家长监督 → AI 识别和提醒 → 会话结算 → 报告 → 后台观察。

### 已确认事实

- 月卡、季卡、年卡使用总时长权益，但所有新访问码统一设置 3 个月有效期。
- 后台改套餐不会同步总时长和有效期。
- 会话结束与额度扣减分两步执行，既不是事务，也不是原子累加。
- 活跃会话未结算时长不会实时计入剩余额度，存在超用可能。
- 标准和高级报告仍输出 Mock 内容。
- 后台采用共享密码；限流只在单实例内存；清理接口没有专用签名。
- 没有自动化测试、持续集成或依赖锁文件。

### 判断或假设

- 当前最有价值的下一步是用最低必要的可靠性修复支撑真实小规模验证，而不是立即建设完整支付和账户系统。
- 套餐如果继续叫月卡、季卡、年卡，用户会自然理解为 30/90/365 天内有效。
- 高级报告的价值尚未验证，先接入更多生成模型可能增加成本而不能证明留存。

### 未知项

- 是否已有正式生产环境和真实用户。
- 线上当前使用 Mock 还是 Qwen。
- 实际售价、成交、退款、留存和供应商账单。
- 监护人同意和第三方模型数据处理是否已有线下文本或流程。

## 2. 触发问题

项目负责人希望根据已发现问题选择下一步优化方案。

如果没有路线选择就直接逐项修复，容易出现两种偏差：

- 过度工程化：在没有用户验证前建设支付、账户和复杂基础设施；
- 过度试验化：带着权益、账目、隐私和 Mock 报告风险直接对外试用。

## 3. 本次目标

- 给出三条边界清晰的推进路线。
- 把必须先决定的套餐和报告规则单独列出。
- 让负责人可以用一个组合完成决策。
- 本轮只形成决策，不修改业务代码。

## 4. 所有路线共同底线

不论选择哪条路线，正式让真实家庭使用前都应满足：

1. 套餐名称、有效期和总时长一致。
2. 会话结算幂等且额度扣减原子化。
3. 不把 Mock 报告包装成正式高级能力。
4. 明确告知摄像头用途、是否存图、第三方模型处理和监护人同意。
5. 至少覆盖访问码、结算和报告权限的关键自动化测试。

## 5. 路线方案

### 方案一：可靠性地基优先

定位：先把系统整理成可稳定维护、可放心交付的产品，再开展用户验证。

#### 实施顺序

1. 统一套餐、有效期、换套餐和退款后的报告访问规则。
2. 用 Supabase 数据库函数完成原子、幂等会话结算，阻止超额使用。
3. 清理旧日额度语义和后台冲突文案。
4. 标准/高级报告暂时降级为真实基础报告或明确 Beta。
5. 增加监护人同意、图片处理说明、Cron 签名和持久限流。
6. 增加依赖锁文件、核心测试、构建检查和 CI。
7. 再建立真实业务指标后台。

#### 收益

- 数据、权益和用户承诺最稳。
- 后续接支付和规模化的返工较少。
- 更适合已经有真实付费客户或即将公开销售的情况。

#### 代价与风险

- 前几轮用户可见的新功能较少。
- 如果尚无用户，部分安全和工程投入可能早于市场验证。

#### 验收

- 套餐权益在创建、换套餐、到期和退款路径一致。
- 同一会话重复结算不会重复扣费，并发结算不丢额度。
- 所有报告内容都有真实数据来源标识。
- 核心业务测试和部署构建自动通过。

### 方案二：最低地基 + 小规模真实验证（推荐）

定位：先修不能带入试用的高风险问题，随后用 10–30 个真实家庭验证价值，不提前建设完整商业系统。

#### 实施顺序

第一轮——最低可靠性：

1. 统一套餐权益；试用阶段减少套餐复杂度。
2. 完成原子、幂等结算和额度上限控制。
3. 暂停标准/高级 Mock 卖点，统一使用真实基础报告。
4. 增加简洁、明确的监护人同意和图片处理说明。
5. 补访问码、结算、报告令牌的关键测试。

第二轮——真实数据：

1. 确认生产环境只使用明确标识的 Qwen 或 Mock 测试模式。
2. 后台增加可信监督会话、摄像头失败率、Qwen/Mock 占比、无法判断率、纠错率和 7 日复用。
3. 建立匿名反馈：报告是否有帮助、提醒是否打扰、下次是否愿意继续。
4. 用固定样本和人工核对建立第一版识别质量基线。

第三轮——根据数据选择：

- 如果监督完成和复用成立，进入账户/支付或高级报告。
- 如果摄像头失败高，优先优化设备流程。
- 如果纠错和无法判断高，优先优化模型、角度和提示。
- 如果提醒恢复低或用户反感，调整提醒策略。

#### 收益

- 在可控风险下最快获得真实答案。
- 避免在需求未验证前建设支付、复杂账户和高级 AI。
- 每轮都有明确数据决定下一步。

#### 代价与风险

- 试用期仍以人工发码和人工运营为主。
- 后台、安全和代码拆分只做最低必要范围。
- 需要负责人能招募并跟进一小批真实家庭。

#### 验收

- 第一轮达到五条共同底线。
- 第二轮能按真实数据计算可信监督、质量、提醒效果和复用。
- 至少完成一个明确观察窗口，并形成继续、调整或停止的结论。

### 方案三：直接商业化建设

定位：在修复地基的同时，直接建设完整销售和家庭账户体系。

#### 实施顺序

1. 完成方案一的可靠性工作。
2. 建立用户、家庭、孩子、商品、订单、支付、退款和权益账本。
3. 自动发码或将访问码升级为正式权益凭证。
4. 建立管理员账号、角色权限、客服工单和财务对账。
5. 建立跨设备报告、到期提醒、续费和增长漏斗。
6. 正式实现标准/高级报告差异。

#### 收益

- 商业闭环完整，适合已有明确订单来源和付费需求。
- 客户、权益、订单和退款可以统一管理。

#### 代价与风险

- 范围最大、决策最多、验证周期最长。
- 当前没有用户、收入和留存证据时，容易做出大量无效建设。
- 支付、身份、儿童数据和客服会同时提高合规与运营复杂度。

#### 验收

- 从下单、支付、权益发放、使用、续费到退款可完整对账。
- 家庭数据、管理员权限和操作审计满足正式运营要求。
- 单位经济性能够按订单和家庭计算。

## 6. 套餐权益选择

### 权益 A：纯时长包

- 将月卡、季卡、年卡改名为 60/180/720 小时时长包。
- 主要按剩余总时长控制，可设置统一且清晰的最长使用期限。
- 优点：逻辑简单，用户容易理解剩余时长。
- 缺点：弱化订阅和续费节奏。

### 权益 B：期限卡 + 总时长上限（推荐）

- 月卡：30 天、3,600 分钟。
- 季卡：90 天、10,800 分钟。
- 年卡：365 天、43,200 分钟。
- 到期或总时长用完任一条件触发即停止。
- 优点：保持现有命名，用户理解自然，也能控制成本。
- 缺点：需要明确未用完时长、升级和退款规则。

### 权益 C：每日额度订阅

- 恢复真正的每日额度，每天重置，并叠加有效期。
- 优点：可限制高强度使用和成本。
- 缺点：规则最复杂，和刚完成的总时长改造冲突，不适合当前阶段。

建议：选择权益 B；MVP 阶段不做复杂“原码换套餐”，升级时创建新权益或由后台做有审计的人工补偿。

## 7. 报告策略选择

### 报告 A：全部使用真实基础报告（推荐）

- 暂时取消对外的标准/高级差异。
- 所有内容来自真实记录和规则统计。
- 等真实家庭证明需要更深报告后再开发。

### 报告 B：标准/高级明确标记 Beta

- 保留套餐入口，但测试内容必须明显标记，不能形成正式承诺。
- 适合只面向知情内测用户。

### 报告 C：立即接入正式高级模型

- 接入真实生成模型，设计提示词、评估集、成本和安全审核。
- 只有已经确认高级报告是购买理由时才建议选择。

## 8. 推荐组合

推荐：

- 主路线：方案二“最低地基 + 小规模真实验证”；
- 套餐：权益 B“期限卡 + 总时长上限”；
- 报告：报告 A“全部使用真实基础报告”。

这个组合先修复权益、账目、隐私和真实性问题，然后用真实数据决定要不要继续投入商业化或高级 AI，风险和投入最平衡。

## 9. 暂不纳入推荐组合

- 支付和完整账户体系；
- 多孩子、多监护人；
- 正式高级生成报告；
- 大规模重构 2,000 行监督页面；
- 完整管理员角色系统；
- 在真实质量数据之前继续增加识别状态。

这些并非不做，而是等待真实使用数据决定优先级。
