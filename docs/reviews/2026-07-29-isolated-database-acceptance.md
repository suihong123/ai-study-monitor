> 负责人：项目负责人 / Codex
> 关联范围：本机隔离 PostgreSQL、migration 18、只读验证 SQL、迁移前后权益快照、数据库事务测试、用户文案、真机验收记录

## 1. 当前基线

- 当前产品阶段：生产仍为 v0.8；v0.9 使用环境重新绑定已完成本地代码和自动测试，尚未执行生产迁移、推送、合并或部署。
- 当前代码/版本：`codex/device-rebind-mvp`，开发版本 v0.9；工作区包含上一轮尚未提交的完整改动。
- 已确认事实：
  - 规则固定为任意连续 15 天最多免费重新绑定 10 次、两次成功至少间隔 60 秒、不扣监督时长。
  - migration 18 从未在生产执行。
  - 本机当前没有 PostgreSQL、Docker 或 Supabase CLI，也没有隔离数据库连接配置。
  - 仓库只提供 `.env.example`，本轮不读取或连接生产数据库。
  - 用户允许建立独立 Supabase 测试项目或其他真实隔离 PostgreSQL。
- 判断或假设：
  - 本机临时 PostgreSQL 足以验证 PostgreSQL 行锁、事务、函数、约束和索引语义，并比内存模拟数据库更可靠、更安全。
  - 19 个脱敏访问码只需覆盖生产数据形态，不需要复制真实访问码、IP、User-Agent、监督内容或儿童数据。
- 未知项：
  - 生产 v0.8 的精确 19 码分布和报告数量；本轮通过覆盖要求的脱敏构造数据验证结构兼容，不把构造数据当作真实生产快照。
  - 真机设备和浏览器需要项目负责人按验收表执行，Codex 无法替代实体手机、平板和摄像头操作。

## 2. 触发问题

- 发生了什么：静态 SQL 和单元测试已通过，但尚未证明真实 PostgreSQL 行锁、事务回滚、迁移兼容和旧令牌失效。
- 证据来源：上一轮复盘和自动验证结果；本机缺少 PostgreSQL 运行时。
- 影响的角色：家长、运营管理员、上线执行者。
- 影响的核心流程：v0.8 数据快照 → migration 18 → 权益对比 → 重新绑定 → 原环境失效。
- 影响的业务/质量指标：权益正确性、重新绑定成功率、并发一致性、旧环境停止率。
- 不处理的后果：可能把只在文本层正确的 SQL 直接带入生产，造成迁移失败、重复计数、分钟变化或两个环境抢占。

## 3. 本次目标

- 目标：在不接触生产的前提下，用真实隔离 PostgreSQL验证 migration 18、19 码兼容、滚动窗口、60 秒、幂等、并发、回滚、令牌轮换和管理员重置。
- 成功标准：
  - 迁移和只读验证 SQL 在真实 PostgreSQL 成功执行；
  - 19 个脱敏访问码的套餐、分钟、状态、环境、会话、记录和报告前后完全一致；
  - 真实数据库规则测试全部通过；
  - 生成可直接填写的真机验收清单和结果记录；
  - 工程检查继续通过。
- 本次范围：隔离数据库初始化/销毁脚本、快照/对比脚本、真实数据库验收脚本、必要缺陷修复、用户端文案统一、验收记录。
- 明确不做：生产数据库、生产部署、远程推送、主分支合并、新业务功能、设备指纹、OAuth、账户体系，以及任何规则调整。

## 4. 规则与口径

- 既定规则不变：15 天、10 次、60 秒、不扣监督时长、单一激活环境。
- 快照全程只读；数据库测试仅修改临时数据库内的脱敏测试数据。
- 迁移前后必须一致：访问码数量、套餐、总/已用/剩余分钟、状态、原环境 ID、历史/活跃会话、记录和报告数量。
- 允许变化：migration 18 新结构、默认配置、空的重新绑定历史及环境扩展字段。
- 用户端主文案统一为“访问码15天内最多可免费重新绑定10次。”

## 5. 方案摘要

- 建议方案：安装本机 PostgreSQL，使用临时数据目录和非默认端口启动；从 v0.8 结构构造 19 个脱敏访问码，执行完整迁移和并行事务测试，结束后停止临时实例。
- 不采用内存模拟库：无法证明 PostgreSQL `FOR UPDATE`、事务回滚、约束和函数行为。
- 不采用生产 Supabase：违反本轮边界。
- 主要风险：
  - 本机构造数据能验证结构兼容，但不能代表生产真实数据分布；
  - PostgreSQL 与 Supabase 扩展/权限环境存在少量差异；
  - 真机部分仍需实体设备人工执行。
- 回滚/降级方式：任何失败均丢弃临时数据库、修复脚本后从干净 v0.8 基线完整重建；不在失败数据库上手工补结果。

## 6. 验收与观察

- 功能验收：首次、同环境、首次重新绑定、60 秒、第 10/11 次、15 天恢复、幂等、并发、回滚、管理员重置。
- 异常路径：函数中途失败、重复请求、两个目标环境并发、原令牌调用。
- 数据验证：迁移前后快照自动差异应为 0。
- 设备/浏览器验证：手机、平板、微信、系统浏览器、监督中被接管、管理员重置。
- 本轮观察：只判断是否具备生产上线条件，不采集经营指标。

## 8. 实施后回写

- 实际改动：
  - 新增 19 码脱敏 v0.8 数据集、只读快照 SQL 和真实 PostgreSQL 自动验收程序；
  - 补充迁移验证 SQL 的报告数量查询；
  - 统一用户可见“重新绑定”文案；
  - 新增隔离数据库结果记录和可填写的真机验收表。
- 验证结果：
  - PostgreSQL 18.4 临时实例仅监听 `127.0.0.1`，未读取或使用生产连接；
  - migration 18 成功，0 个 warning、0 次锁等待、0 次回滚；1 条 `if exists` 兼容性 NOTICE；
  - 19 个访问码、16 个历史会话、6 个活跃会话、48 条监督记录和 10 份报告统计迁移前后完全一致；
  - 9 条只读验证查询通过，3 个函数与 `schema.sql` 的 PostgreSQL 函数定义一致；
  - 首次绑定、同环境、第 1/10/11 次、15 天滚动恢复、60 秒、幂等、双连接并发、强制事务回滚和管理员重置全部通过。
- 发现与修复：
  - 当前系统没有独立报告表，已将报告快照口径明确为成功的 `report_%` AI 调用日志；
  - 原用户页面混用“重新激活”，已统一为“重新绑定”，主说明采用负责人指定文案；
  - 本机系统版本无法通过 Homebrew 安装 PostgreSQL，改用仅本地监听、结束自动销毁的嵌入式 PostgreSQL 运行时；数据库测试仍为真实 PostgreSQL。
- 遗留问题：
  - 脱敏 19 码验证不能替代生产真实 19 码的迁移前后只读快照；
  - 未覆盖 Supabase 托管环境的权限、扩展和网络差异；
  - 本次隔离数据库阶段未覆盖实体设备；后续核心真机验收已由项目负责人完成并确认。
- 最终状态：隔离数据库验收通过；后续托管数据库、Preview、真实 Qwen 和核心真机验收也已完成。当前只进行 Release Candidate 整理，尚未生产迁移、推送、合并或部署。
