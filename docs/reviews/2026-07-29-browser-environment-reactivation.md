# 优化前复盘：浏览器使用环境重新激活

> 日期：2026-07-29
> 状态：功能验收已完成，待 Release Candidate 审核
> 负责人：项目负责人 / Codex
> 关联范围：首页、监督页、访问码与重新激活 API、数据库迁移、运营后台、自动测试

## 1. 当前基线

- 当前产品阶段：v0.8 已在生产环境进行小规模真实使用观察，v0.9 自助换绑尚未执行生产迁移、推送或部署。
- 当前代码/版本：`codex/device-rebind-mvp`，提交 `ea6c5bd`，开发版本 v0.9。
- 与本次相关的现有流程：浏览器以 `localStorage` 随机 UUID 标识使用环境；首次验证自动绑定；原 v0.9 方案提供 3 次免费换绑，之后扣监督时长，并带可配置冷却。

### 已确认事实

- `device_id` 识别浏览器存储环境，不是物理手机或平板。
- 同一物理设备切换微信浏览器、系统浏览器或无痕模式时可能产生不同 `device_id`。
- 生产 `PROD_CODE_REDACTED` 的脱敏历史已出现同型号手机在微信被拒、随后从系统浏览器成功进入的情况。
- 纯网页无法低成本、稳定地跨浏览器识别同一物理设备。
- 当前真实家庭数量较少，项目仍在商业验证阶段，优先降低正常家庭切换环境的使用摩擦。
- 生产仍为 v0.8，`migration_2026_18_device_rebind_mvp.sql` 从未执行，可以直接整理为最终 v0.9 迁移。
- 访问码永久总时长、会话原子结算、报告数据和现有 19 个访问码权益不得改变。

### 判断或假设

- 任意连续 15 天 10 次免费重新激活足以覆盖家庭在手机、平板、微信和系统浏览器之间的正常切换。
- 60 秒最小间隔可降低脚本抢占和瞬时并发，不会明显影响真实家庭操作。
- 现阶段设备资料只用于展示和人工排查，不作为强安全身份凭证。

### 未知项

- 真实家庭 15 天内的重新激活次数分布。
- 微信、iOS Safari 和 Android 系统浏览器对 `localStorage` 的实际清理频率。
- 不同网络出口的地区识别能力；本轮只保留轻量异常标记，不做强地理封禁。

## 2. 触发问题

- 发生了什么：原 v0.9 将浏览器环境误称为物理设备，并用终身 3 次、24 小时冷却和扣监督时长处理正常环境切换。
- 证据来源：设备识别专项审计、脱敏生产访问码只读日志、当前 `lib/device.ts` 与换绑迁移函数。
- 影响的角色：家长、运营/客服、系统维护者。
- 影响的核心流程：访问码验证 → 使用环境准入 → 创建/恢复监督 → 旧环境失效。
- 影响的业务/质量指标：首次监督启动率、家庭复用率、人工解绑量、重新激活成功率、权益投诉。
- 不处理的后果：正常用户可能被误判并损失监督时长；旧监督页面仍开着摄像头重试；后台无法准确解释滚动窗口资格。

## 3. 本次目标

- 目标：以低成本实现“单浏览器环境激活 + 滚动 15 天最多 10 次免费重新激活”，保护监督权益和单环境原则。
- 成功标准：
  - 首次激活和同环境进入不计次数；
  - 最近 15 天成功记录少于 10 次时允许重新激活；
  - 60 秒内第二次真实重新激活被拒；
  - 第 11 次被拒并返回下一次可用时间；
  - 所有重新激活均不改变总时长、已用时长或剩余时长；
  - 幂等、并发、绑定更新、成功日志和旧令牌失效由同一数据库事务控制；
  - 旧环境收到失效响应后停止摄像头、定时器和请求，清理状态并返回首页；
  - 管理员重置不计入用户 10 次额度并记录原因。
- 本次范围：最终 v0.9 迁移/schema/验证 SQL、验证与重新激活 API、首页弹窗、监督失效处理、后台配置/详情/历史/重置、测试和基线文档。
- 明确不做：物理设备指纹、Cookie 签名、OAuth、账户、手机验证码、原生 App、多环境同时在线、付费换绑、时长换绑、自动封号。

## 4. 规则与口径

- 激活单位：一个访问码同一时间只激活一个浏览器或使用环境 UUID。
- 滚动窗口：数据库当前时间往前 `rebind_window_days` 天，只统计 `device_rebind_logs.success=true` 且 `result_code='rebound'` 的用户重新激活记录。
- 默认配置：15 天、10 次、60 秒；边界分别为 1–90、1–100、10–86400。
- 首次激活、同环境进入、取消、失败、重复幂等回放和管理员重置不进入滚动次数。
- 兼容旧数据：选择方案 B。由于迁移未上线，直接删除未上线的 `free_rebind_count` 和 `rebind_cost_minutes`，避免形成无效存量口径；既有 19 个访问码迁移后历史计数为 0。
- 权益影响：重新激活函数不得写入 `used_minutes`、`used_minutes_today`、`total_minutes` 或会话时长。
- 安全口径：客户端 UUID 只是浏览器环境标识；单环境、频率、滚动次数、幂等、日志和令牌轮换均由数据库控制。

## 5. 方案摘要

- 建议方案：
  - 重写未上线的 migration 18 和完整 schema，以历史表作为滚动窗口事实来源。
  - 数据库函数锁定访问码，先复用幂等结果，再判断同环境、60 秒间隔和 15 天上限，成功时原子更新环境、轮换活跃令牌、写日志。
  - 验证接口返回已用次数、上限、确认后次数、是否允许、限制原因和下一次可用时间。
  - 用户端统一使用“使用环境/重新激活”，成功后显示明确反馈。
  - 监督页将令牌失效视为环境接管，执行完整本地停止和退出。
  - 后台展示当前环境、15 天次数、下一次可用时间、频繁标记和重新激活历史；管理员重置沿用现有后台鉴权并要求原因。
- 备选方案：保留 `free_rebind_count` 但停用。否决原因是迁移尚未上线，保留无效字段会制造双重口径和维护成本。
- 主要风险：
  - 纯前端 UUID 可伪造，只能作为低成本环境许可而非强身份。
  - 浏览器清理存储会被视为新环境。
  - 旧页面跳转提示需要跨页面保存，不能只依赖瞬时组件状态。
  - SQL 并发行为必须通过真实数据库人工验收，静态测试不能完全替代。
- 回滚/降级方式：应用端关闭重新激活确认入口并恢复不同环境拒绝；数据库新增表和字段可保留，紧急停用可把全局配置设为禁用，不能回滚已合法完成的环境切换。

## 6. 验收与观察

- 功能验收：首次、同环境、1–10 次、第 11 次、15 天滚动恢复、60 秒间隔、成功提示、上限提示。
- 异常路径：重复幂等键、响应丢失、不同环境并发、数据库失败、无效/冻结访问码、旧令牌、管理员重置。
- 数据验证：19 个现有码的套餐/总时长/已用时长/会话/报告不变；历史计数为 0；成功日志可还原前后环境。
- 设备/浏览器验证：微信↔系统浏览器、手机↔平板、清理 localStorage、旧环境正在监督、新环境恢复会话。
- 上线后观察指标：重新激活请求/成功/失败、15 天次数分布、60 秒拦截、达到上限、管理员重置量、重新激活后监督启动率。
- 观察窗口：首批 3～5 个真实家庭或上线后 15 天。

## 8. 实施后回写

- 实际改动：
  - 最终 migration 18 和完整 schema 改用成功历史滚动计数，删除未上线的终身免费次数和换绑费用字段。
  - 新增 15 天/10 次/60 秒配置、状态查询函数、原子重新激活函数和管理员原子重置函数。
  - 数据库函数在访问码行锁内完成幂等复用、资格判断、环境更新、活跃令牌轮换、成功/失败历史和轻量异常标记；不写任何分钟字段。
  - 验证接口返回服务端结构化状态；重新激活接口在应用限流前优先复用已有幂等响应。
  - 首页完成新环境确认、次数/限制和成功反馈；旧监督页在令牌失效后停止摄像头、分析、心跳、声音和本地状态并返回首页。
  - 后台改为窗口/上限/间隔配置，增加当前环境、滚动次数、下一次可用、异常标记、历史和填写原因的管理员重置。
  - 更新项目基线、业务状态、迭代规则、README、上线/停用/回退说明及只读验证 SQL。
- 验证结果：
  - `npm run typecheck` 通过。
  - `npm run lint` 通过，无警告或错误。
  - 3 个测试文件共 35 项通过，其中使用环境重新激活专项 27 项。
  - `npm run build` 通过，首页、监督页、后台和重新激活 API 均进入生产构建。
  - `git diff --check` 通过。
  - migration 与 schema 中 3 个数据库函数文本一致；验证 SQL 经静态测试确认只读。
  - 当前环境没有 PostgreSQL/Supabase 本地运行时，未实际执行 SQL；数据库并发、迁移和 19 个访问码兼容仍须在隔离/生产前环境验证。
- 与原方案的差异：
  - 终身 3 次免费、后续扣 30 分钟、余额不足拒绝、付费换绑和 24 小时冷却全部删除。
  - 产品定义从“物理设备换绑”调整为“浏览器使用环境重新激活”。
  - 管理员重置独立记为 `action_source='admin'`，不占用户滚动次数。
- 遗留问题：
  - `device_id` 仍可因清理存储、无痕或切换浏览器变化，也可被客户端伪造；本轮不作为强身份。
  - 没有 IP 地理库，当前记录 IP 并对大量不同 User-Agent 标记，无法可靠判断“不同地区”。
  - 应用接口限流仍是单实例内存实现；核心 60 秒与 15 天规则由数据库保证，但规模化前仍建议改为共享限流。
  - 静态测试不能替代真实 Postgres 行锁、事务回滚和两环境并发验收。
- 基线文档更新：`PROJECT_BASELINE.md` 升级到 1.4，并同步更新业务状态、迭代机制、资料中心、根 README 和复盘索引。
- 最终状态：后续隔离/托管 PostgreSQL、Preview、真实 Qwen 和核心真机验收均已完成；当前进入 Release Candidate 整理。生产数据库仍未迁移，未推送、未合并、未部署。
